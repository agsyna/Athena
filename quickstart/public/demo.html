Normalization

Normalization is the process of structuring a relational schema to reduce redundancy and prevent update anomalies. First normal form requires every column value to be atomic — no repeating groups, no lists packed into a single field. Second normal form additionally requires that every non-key attribute be fully functionally dependent on the whole primary key, which only bites when the key is composite. Third normal form removes transitive dependencies: a non-key attribute must not determine another non-key attribute. Boyce-Codd normal form tightens this further, requiring that every determinant be a candidate key. Normalizing too aggressively trades write-side integrity for read-side join cost, which is why reporting schemas are often deliberately denormalized.

Indexing

An index is an auxiliary structure that lets the engine locate rows without scanning the whole table. The dominant implementation is the B+ tree, where internal nodes hold only keys and all records live in the leaves, which are linked to make range scans cheap. Every index accelerates reads but taxes writes, since each insert, update, and delete must maintain the index as well as the table. A composite index on (a, b) can serve a query filtering on a alone, but not one filtering on b alone — the leftmost-prefix rule. A covering index contains every column a query needs, so the engine can answer from the index and never touch the heap.

Transactions and isolation

A transaction is a unit of work that is atomic, consistent, isolated, and durable. Isolation levels trade correctness for concurrency. Read uncommitted permits dirty reads. Read committed prevents those but still allows non-repeatable reads, where the same row changes between two reads in one transaction. Repeatable read prevents that but can still admit phantoms, where new rows matching a predicate appear. Serializable forbids all three, at the cost of throughput. Most engines implement the middle levels with multi-version concurrency control, keeping several versions of a row so readers never block writers.

Join strategies

The planner chooses between three main physical joins. A nested loop join scans the outer relation and probes the inner one per row — excellent when the outer side is tiny and the inner side is indexed on the join key. A hash join builds an in-memory hash table over the smaller relation and streams the larger one past it, which is the usual choice for large unsorted equijoins but degrades badly if the build side spills to disk. A merge join requires both inputs sorted on the join key and then walks them in lockstep, which is nearly free when an index already provides the ordering. Only hash join is restricted to equality predicates.

Query planning

The optimizer converts a declarative query into a physical plan by estimating the cost of alternatives. Costs are driven by statistics — row counts, column histograms, distinct-value estimates — which are sampled and therefore stale between refreshes. Selectivity estimation errors compound multiplicatively through a join tree, which is why a plan that is wrong at the leaves is usually catastrophically wrong at the root. This is the single most common cause of a query that was fast last week and is slow today.
